# Название решения

Файл назван по образцу `010-имя-решения.md`. Номер служит адресом, по которому на решение ссылаются из отчётов.

Статус бывает `proposed` у предложенного, `accepted` у принятого, `rejected` у отклонённого и `superseded` у заменённого другим решением со ссылкой на замену.

Разделы ниже повторяют [MADR 4](https://adr.github.io/madr/).

## Контекст и проблема

В текущей реализации, когда API синхронно отправляет события в сервис уведомлений, есть следующие проблемы:
1. Увеличение времени ответа API: необходимо подождать, пока внешний сервис подтвердит получение события. В случае, если внешний сервис медленный, время ответа от API может значительно увеличиться или вообще ожидание может прекратиться по таймауту. Из опытов было выявлено, что при запуске провайдера в режиме `slow` выполнение запроса заняло 2,25 с при бюджете в 1,5 с.
2. В случае, если внешний сервис недоступен по той или иной причине, событие не запланировано к повтору, оно может быть утеряно, так как не сохраняется в персистентном хранилище. Из отчера видно, что при запуске провайдера в режиме `unavailable` поездка создалась в рамках бюджета по времени, но задание на повторную отправку не сохранилось, работа утеряна.

## Какие варианты сравнивали

1. Прямые вызовы (текущая реализация) - система фиксирует событие и вызывает внешние сервисы. Данный вариант не укладывается в бюджеты, а также не предустматривает повторов и восстановления. В случае добавления дополнительных сервисов необходимо будет изменять API сервиса такси, а проблема с ожиданием и потерей работы только усугубится. Способов восстановления нет.
2. Сохраненные задания - сохранение поездки и задания в отдельную таблицу заданий в рамках одной транзакции + воркеры, которые занимаются обработкой этой таблицы. Сервис такси все еще напрямую взаимодействует со внешними сервисами, но в рамках фоновых задач. Сервис воркеров должен знать все внешние сервисы, с которыми необходимо взаимодействовать, добавление, удаление или изменение набора сервисов потребует изменения логики воркеров. Необходимо продумывать параллельную обработку таблиц воркерами, блокировки записей, повторную отправку записей, восстановление самого воркера. После сбоя воркер подбирает незавершённые задания из таблицы и повторяет их обработку. Для пересчета показателей необходимы изначальные факты, таблица с заданиями может служить таким источником для восстановления, если намеренно сохранять в ней нужные данные и историю.
3. Журнал фактов - transactional outbox + Kafka. Для API сервиса такси больше не будет необходимости напрямую взаимодействовать со внешними сервисами, нет проблемы утери событий (потребитель фиксирует позицию чтения после сохранения факта для отчёта или задания на отправку). Сама Kafka при этом становится источником событий для восстановления, выбраная настройка: 7 суток хранения фактов плюс запас. Однако возникают риски сетевых ошибок между продьюсером, брокером и консьюмером, должны быть обеспечены механизмы повторной отправки сообщений для всех сторон.

## Решение

Принято решение добавить отправку событий через transactional outbox + Kafka, так как журнал фактов позволяет независимо читать факты разными обработчиками, а также он становится источником фактов для перерасчета на 7 суток без сохранения изначальных фактов на стороне приложения такси.

Граница транзакции для сервиса такси - сохранение поездки и сообщения в рамках одной транзакции.

`tripId` является ключом сообщения (ключом партиции в Kafka).
`eventId` является параметром для дедупликации.

Правила отчета - считать создания и завершения поездок, суммировать стоимость поездок по городу и дню факта без учета событий, которые являются дублями (то есть дедуплицировать факты, не учитывать их в подсчетах).

## Последствия

Позитивное влияние: работа больше не утеряна, настроены повторы отправки при сбое внешних сервисов, Kafka также является краткосрочным хранилищем данных.
Негативное влияние: возможны сетевые сбои, необходимо корректно настроить повторную отправку на стороне продьюсера и повторный прием на стороне консьюмера: сообщения должны иметь ключ идемпотентности и корректно обрабатывать повторы. Должна быть реализована обработка ошибок: retry policies и правила попадания в Dead Letter Queue.

Цена решения: брокер должен быть расположен в идеале на отдельном сервере, то есть это дополнительная машина и ее обслуживание.

## Подтверждение

Проверка работоспособности решения: внешний сервис останавливается на 10 минут и затем восстанавливается. Проверяется сохранность всех фактов, восстановление свежести внешними сервисами за 5 минут, проверяется, что дубликаты были учтены корректно (повторное сообщение не отправилось, счетчики и суммы в отчете не учитывали дубликаты). Также необходимо запустить перерасчет отчета за последние 7 дней и сверить счетчики, суммы, а также что новые отправки уведомлений не были запущены.
